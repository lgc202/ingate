# Ingate 接口设计约束

这份文档用于约束仓库里的接口设计，目标不是追求“到处可替换”，而是避免为了测试、为了想象中的未来扩展、或者为了形式上的解耦而过早抽象。

## 核心原则

### 1. 先具体实现，再按需发现接口

默认先写具体类型，让真实业务路径先成立。只有在后续演进中出现明确需求时，才考虑把行为提炼成接口。

这里说的“明确需求”通常包括：

- 真实存在多个生产实现
- 存在稳定的外部协作边界
- 需要打破包循环依赖
- 调用方只依赖实现中的一小部分能力，且这个依赖面稳定

如果这些前提都还不存在，就不要先给结构体配一个接口。

### 2. 接口优先定义在消费者侧

接口表达的应当是“调用方需要什么”，而不是“实现方拥有什么”。因此优先在消费者侧定义最小接口，只暴露调用方真正用到的方法集。

这能避免两类常见问题：

- 在实现侧定义出大而全接口，迫使调用方依赖不需要的方法
- 为了复用一个接口，把不相关职责硬塞进同一抽象

### 3. 小接口、单一职责、可组合

保留下来的接口应尽量满足：

- 方法少
- 职责单一
- 每个方法语义清晰、不重叠
- 能通过组合形成更大契约，而不是一开始就定义胖接口

如果一个接口越来越大，通常不是“能力更完整了”，而是职责边界出了问题。

## 明确反对的做法

### 1. 不要为了测试方便先造接口

“测试需要 mock，所以先抽一个接口”不是默认正当理由。

在这个仓库里，优先考虑这些方式：

- 直接测试具体类型
- 在真实边界上用 fake client / reactor / 轻量 fake object
- 对纯函数和纯转换做直接测试
- 如果某类 orchestration 测试只能靠 recording mock 才成立，优先评估它是不是低价值测试，必要时直接删除

如果一个接口除了让测试更容易写之外，并没有改善生产代码中的真实解耦关系，就不该留在生产代码里。

### 2. 不要为了“未来可能扩展”预设接口

“以后也许会有第二个实现”不应成为当前抽接口的理由。

接口应该从真实依赖点和真实依赖需求中被发现，而不是为了想象中的将来被发明出来。YAGNI 在这里同样适用。

### 3. 不要保留单实现 + 纯转调的中间层

如果一个接口或默认实现满足下面这些特征，就应优先回退：

- 当前只有一个生产实现
- 主要逻辑只是转调另一个具体函数或具体类型
- 存在的主要原因是注入 mock / stub
- 删除后代码路径会更直接、更容易读

这类抽象通常只会增加间接层、导航成本和理解成本。

## 在这个仓库里的判断尺子

做接口设计判断时，先问下面几个问题：

1. 这里是否真的存在稳定的协作边界？
2. 调用方是否只需要很小的一部分行为？
3. 不抽接口是否会造成真实耦合问题，而不是测试不方便？
4. 这个接口放在消费者侧是否更自然？
5. 删除这层接口后，生产代码是否会更直接？

如果前四个问题都答不稳，而第五个问题答案是“会”，那通常就应该删接口。

## 当前仓库中的保留倾向

更可能值得保留的小接口：

- 发布边界
- 存储装配边界
- 框架注册边界
- 明确的跨模块 side-effect 边界

更可能应回退的抽象：

- 单实现包装层
- 纯转调 compiler / translator 骨架
- 主要服务测试替身注入的 controller 依赖接口
- 面向多个资源的大而全 store 接口

## 测试策略配套原则

测试应尽量围绕这些层次建设：

- 纯函数 / 纯转换测试
- 基于真实边界的 fake client/reactor 测试
- 编译、联调、verify 脚本驱动的回归验证

避免把“能否轻松写 mock”当成生产设计的主导因素。
