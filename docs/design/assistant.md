# Ingate 运维助手架构设计

状态：目标设计；查询诊断与首批资源创建审批已实现

目标读者：Ingate 维护者和后续参与实现的开发者

## 1. 背景

Ingate 已经具备网关、路由、服务、治理策略、插件和观测分析等能力。随着配置项和运行数据增多，用户需要在多个页面之间查找信息，才能完成一次故障定位或配置调整。

运维助手不是新的流量代理，也不负责承载用户自己的 Agent。它是 Ingate 控制台的一项管理能力，使用自然语言协助用户理解当前系统、定位问题、生成配置变更，并在获得授权后执行操作。

本设计描述完整目标架构。实现按可验收场景逐步交付，但会话、记忆、工具、审批和 Agent 协作必须遵循同一套边界，避免后续增加能力时重写主流程。

### 当前实现

当前已经完成查询诊断和第一段可写闭环：

- 独立的 `ingate-assistant` 组件和 Console 统一入口
- OpenAI 兼容与 Anthropic 模型连接，可直连模型端点或经过 Ingate AI Route
- 基于 Eino ADK 的单 Agent 工具调用循环
- Gateway、Route、Service、流量分析、失败请求、请求明细和 Caller Token 额度等 8 个查询工具
- 创建 Gateway 和普通 HTTP Service 的 2 个可中断工具；首次调用只生成规范化提案，批准后才从 checkpoint 恢复并写入
- 基于 Eino `StatefulInterrupt`、checkpoint 和 `ResumeWithParams` 的人工审批闭环
- MySQL 中的模型连接、会话、Execution、Execution Step、消息、配置提案和 Eino checkpoint
- Redis Stream 中用于 SSE 断线重连的短期事件
- 后台 Worker、Agent 执行租约、取消和过期状态收敛

当前不支持更新、删除、Route、模型 Service、批量变更、预授权、长期记忆、专业 Agent、MCP 工具源、定时任务或自动修复。除“当前实现”和明确描述现有表结构的段落外，本文其余章节描述目标约束，不表示对应能力已经对外提供。

## 2. 设计目标

运维助手需要支持以下完整能力：

- 结合当前控制台页面和资源回答配置问题
- 基于实时配置、请求记录和流量指标进行故障诊断
- 生成 Gateway、Route、Service、Caller、Policy 和 Plugin 的变更提案
- 对有副作用的操作执行权限检查、差异预览、审批和审计
- 保存会话、用户明确设置的偏好和经过确认的处理结论
- 把复杂任务委派给具有独立工具权限的专业 Agent
- 接入内置 Go 工具、AgentTool 和外部 MCP 工具
- 执行定时巡检、周期报告和经过预授权的自动化任务
- 记录模型、工具、审批和最终结果的完整执行链路
- 通过固定评测场景验证模型或 Prompt 变更没有破坏现有能力

## 3. 已确定的架构决策

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 新增业务组件 | `ingate-assistant` | 对话流式响应、模型调用和长任务生命周期不应继续堆入 Admin API |
| Agent 框架 | Eino ADK | 提供 Go 原生 ChatModelAgent、AgentTool、中断、检查点和恢复能力 |
| 产品入口 | Console 统一入口 | 用户不需要认识新的管理地址；Console 将助手请求代理到 Assistant |
| 系统操作入口 | Admin API | Assistant 不访问 etcd，也不绕过现有业务校验和产品协议 |
| 短期状态 | Redis | 只保存可丢失、可重建的 SSE 流式事件 |
| 持久化状态 | MySQL + sqlc | 保存模型连接、会话、Execution、Execution Step、消息、配置提案和 Eino checkpoint |
| 模型连接 | Eino 官方模型适配器 | 可直连 OpenAI 兼容或 Anthropic 端点，也可经过 Ingate AI Route |
| 内部工具 | 进程内 Go Tool | 保持类型安全，避免为内部调用额外增加 MCP 网络边界 |
| 外部工具目标 | MCP | 使用标准协议接入 GitHub、Prometheus、告警平台等系统 |
| 多 Agent 目标 | AgentTool | 专业 Agent 作为根 Agent 的受控工具，避免自由的 Agent 间互调 |

Assistant 单独部署不是为了增加管理层级，而是为了隔离两类不同负载：Admin API 继续承担短请求、确定性业务校验和产品协议；Assistant 承担模型调用、SSE 长连接、中断恢复和后台任务。Assistant、模型、Redis 或 MySQL 不可用时，现有控制面和数据面仍应独立工作。

## 4. 系统位置

```text
Browser
   |
   v
Console
   |-- /api/* ----------> Admin API
   `-- /assistant/* ----> Assistant
                             |-- model request ------> configured model endpoint
                             |-- product operation -> Admin API
                             |-- stream events ------> Redis
                             `-- durable state ------> MySQL

Admin API
   |-- declarative resources --> API Server
   `-- observations -----------> Analytics
```

Assistant 调用 Admin API，不允许 Admin API 再反向调用 Assistant。这样可以保持控制链路单向，避免形成循环依赖。

目标中的专业 Agent、意图判断、记忆、工具和调度都属于 `ingate-assistant` 内部模块，不拆成独立服务。扩容时可以使用同一个二进制分别运行交互请求实例和后台任务实例，但它们仍属于同一个组件和同一套代码。

Console、Assistant 和 Admin API 使用明确版本的产品协议。后续需要支持跨版本独立部署时，再增加 Admin API 能力协商；当前同一版本发布，不提前维护无人使用的协议探测。

## 5. 用户交互模型

产品只向用户呈现“运维助手”，不暴露根 Agent、专业 Agent、工具调用协议或检查点等实现概念。

一次用户请求可能进入以下交互方式：

| 方式 | 示例 | 系统行为 |
| --- | --- | --- |
| 解释 | “Token 额度是怎么计算的？” | 根据正式文档回答，不查询实时状态 |
| 查询 | “这条路由当前是否已经生效？” | 查询资源和 Status 后回答 |
| 诊断 | “最近半小时为什么 5xx 增多？” | 规划查询步骤，收集证据后给出结论 |
| 变更 | “把 `/orders` 转发到订单服务” | 生成变更提案，审批后执行 |
| 自动化 | “每天上午检查即将过期的证书” | 创建定时任务并明确作用范围和通知方式 |

交互方式不是持久化资源，也不要求额外的分类模型。它只是 Assistant 在一次请求中选择执行路径的结果。

## 6. 请求上下文与意图判断

### 6.1 上下文来源

Assistant 使用三类上下文：

1. **显式页面上下文**：Console 传递当前页面、资源类型、资源 ID、筛选时间和用户时区。
2. **会话上下文**：当前对话中已经确认的目标、工具结果摘要和未完成事项。
3. **系统上下文**：当前用户身份、权限、可用工具、模型能力和数据源健康状态。

页面上下文必须由 Console 明确提供。模型不能根据页面标题、资源名称或上一轮对话猜测当前资源 ID。

### 6.2 判断顺序

```text
收到用户消息
  -> 校验页面和用户上下文
  -> 判断是否可以直接回答
  -> 根据上下文缩小可用 Agent 和工具集合
  -> 模型选择工具或专业 Agent
  -> 服务端按工具风险执行、要求审批或拒绝
  -> 汇总证据并生成回答
```

不增加常驻的意图分类模型。自然语言目标由支持结构化工具调用的模型理解，权限、风险和审批由确定性代码判断。

信息不足且不同选择会产生不同结果时，Assistant 只提出影响执行的澄清问题。例如存在两个同名 Service 时，需要用户选择目标；可以从当前 Route 唯一推导 Service 时，不再重复询问。

## 7. Agent 组织

### 7.1 根 Agent

根 Agent 负责：

- 理解用户目标
- 组合页面、会话和系统上下文
- 选择直接工具或专业 Agent
- 控制总步骤数和总工具调用次数
- 汇总最终回答和证据完整性

根 Agent 不直接拥有所有领域工具。工具规模增加后，向单一模型暴露全部工具会降低选择准确率，也会放大权限范围。

### 7.2 专业 Agent

| Agent | 职责 | 主要工具范围 |
| --- | --- | --- |
| 配置 Agent | 解释和调整 Gateway、Route、Service、Certificate、Caller | 声明式资源查询、引用检查、变更提案 |
| 流量诊断 Agent | 分析请求失败、延迟、路由命中和服务端点 | 请求记录、趋势、资源排行、配置关联 |
| AI 用量 Agent | 分析模型调用、Token、额度和线路表现 | AI 用量、模型调用、Caller 和额度策略 |
| 插件 Agent | 检查插件源、安装状态、版本和依赖策略 | 插件目录、安装信息、依赖关系和策略 |
| 知识 Agent | 查询正式文档、操作手册和经过确认的案例 | 文档检索和知识来源工具 |

专业 Agent 使用 Eino AgentTool 接入根 Agent。每个专业 Agent 具有独立系统指令、工具白名单和上下文范围，不共享未经过筛选的完整对话。

跨领域任务由根 Agent 依次调用多个专业 Agent。专业 Agent 不能自行终止根任务，也不能绕过根 Agent 调用其他专业 Agent。

专业 Agent 不能调用自身或其他 AgentTool。根 Agent 对一次执行设置总步骤、工具调用、模型 Token、持续时间和委派深度上限；AgentTool 的输出按工具结果处理，经过大小限制、字段过滤和完整性检查后才能进入根 Agent 上下文。专业 Agent 的有效权限始终是用户权限、根 Agent 授权范围和自身工具白名单的交集。

表中的专业 Agent 是目标领域划分，不要求一开始全部启用。只有工具数量和固定评测证明根 Agent 的选择准确率不足时，才把对应工具收敛为 AgentTool；这个变化不改变工具协议、权限或审计链路。

## 8. 模型连接

模型连接是可在线修改的业务设置，保存在 MySQL 中，不写入组件 YAML，也不是网关声明式资源。YAML 只保留监听地址、MySQL、Redis、日志等进程启动所需配置。

“连接方式”和“模型协议”是两个不同维度：连接方式决定请求发往模型厂商还是 Ingate，模型协议决定 Assistant 与该端点交换消息的格式。协议差异只存在于模型适配层，会话、Execution、工具和事件协议不感知具体厂商。

当前模型连接包括：

- 连接方式：直连模型厂商或经过 Ingate
- 模型协议：OpenAI 兼容或 Anthropic
- 服务地址
- API Key
- 模型名
- 请求超时
- 最大输出 Token
- Anthropic 扩展思考预算

连接方式表达不同的产品语义：

| 连接方式 | 可用协议 | 服务地址 | 模型名 | 适用场景 |
| --- | --- | --- | --- | --- |
| 直连模型厂商 | OpenAI 兼容、Anthropic | 厂商 API 地址 | 厂商真实模型名 | Assistant 不依赖 Ingate 数据面即可工作 |
| 经过 Ingate | OpenAI 兼容 | Ingate 数据面地址 | AI Route 对外发布的模型名 | 复用 Ingate 的模型选路、访问控制、额度和观测能力 |

经过 Ingate 时不在 Assistant 中保存 Route ID。运行时请求只需要数据面地址、对外模型名和调用凭据；Route ID 属于控制面内部标识，保存它会引入资源变更后的失效关联。

默认表单选择“经过 Ingate”，便于用户复用网关治理能力；用户也可以明确切换为直连。每次 Execution 开始时读取当前设置并创建不可变的模型连接，设置更新只影响之后开始的 Execution，不会让进行中的对话请求切换线路。

API Key 只写入、不回显；查询接口仅返回是否已经配置凭据。没有完成模型设置时，Assistant 可以管理会话，但拒绝开始模型调用并返回明确的“模型未配置”状态。

系统指令和 Agent 最大迭代次数属于产品执行逻辑，由 Assistant 版本代码维护，不混入用户配置的模型连接。这样升级提示词或执行边界时可以随版本评审和发布，也不会把系统安全约束交给普通配置接口修改。

直连模式使用 Eino 官方 OpenAI 和 Claude 适配器，不在 Ingate 内自行实现厂商消息协议。“OpenAI 兼容”只约束传输格式，不假设所有兼容端点的能力完全一致。后续增加厂商专有协议时，在模型适配层增加对应的官方适配器，不把厂商差异散落到 Agent、会话和工具实现中。

### 8.1 推理内容

部分模型端点会显式返回 reasoning 或 thinking 内容。Assistant 将这部分内容与最终回答分开处理：

- 流式阶段分别发送 `message.reasoning.delta` 和 `message.content.delta`
- Execution 成功后把两部分内容写入同一条助手消息，Console 可以分区展示
- 生成后续回复时只把最终回答作为历史消息发送，不把已保存的推理内容再次加入上下文
- API Key、系统指令、工具内部结果和厂商未返回的模型内部状态不属于推理内容

Anthropic 协议可以通过推理预算主动开启扩展思考；预算为 0 时不主动开启。OpenAI 兼容端点是否返回推理内容由对应服务决定，Assistant 只消费端点明确返回的结构化字段，不根据最终回答猜测或生成“思考过程”。

## 9. 工具体系

### 9.1 工具来源

| 来源 | 适用范围 | 执行位置 |
| --- | --- | --- |
| 内置 Go Tool | Ingate 自身配置与观测 | Assistant 进程内 |
| AgentTool | 专业 Agent 委派 | Assistant 进程内 |
| MCP Tool | 外部平台和用户自定义工具 | 独立 MCP Server |

数据面 Wasm 插件和 Assistant 工具是两套不同体系。插件处理业务流量，Assistant 工具帮助用户查询和操作管理系统，不能因为都叫“扩展”而共用生命周期模型。

内置 Go Tool 只能随 Ingate 代码发布，不支持用户动态加载进程内代码。用户自定义工具统一通过 MCP 接入，避免把第三方代码加载到 Assistant 进程。

### 9.2 工具定义

每个工具必须声明：

- 稳定名称和版本
- 用途以及不适用场景
- 输入和输出 JSON Schema
- 是否读取实时状态
- 风险等级和副作用
- 所需用户权限
- 超时、最大结果大小和最大分页范围
- 是否幂等、是否允许自动重试
- 可能的失败原因
- 数据来源和结果完整性表达方式

工具描述用于模型选择工具，但服务端不能依赖模型遵守描述来保证安全。

### 9.3 风险等级

| 等级 | 类型 | 默认处理 |
| --- | --- | --- |
| 读取 | 查询配置、指标或文档 | 权限通过后直接执行 |
| 模拟 | 校验配置、生成差异或预测匹配结果 | 直接执行并标记为模拟结果 |
| 准备变更 | 生成变更提案 | 保存提案并要求审批 |
| 执行变更 | 修改 Ingate 或外部系统 | 根据授权策略审批或拒绝 |
| 高风险操作 | 删除关键资源、批量修改、改变安全边界 | 强制逐次审批，不允许自动授权 |

### 9.4 内置工具边界

内置工具调用 Admin API，不直接访问 API Server、etcd、ClickHouse 或数据面组件。工具应面向用户任务组织，而不是简单暴露通用 CRUD 或任意 HTTP 请求。

当前工具包括：

- 查询 Gateway、Route、Service 及 Route 关联配置
- 查询请求记录、流量趋势、错误分布和 AI 用量
- 查询 Caller Token 额度
- 生成创建 Gateway 或普通 HTTP Service 的完整配置提案

工具结果必须包含数据来源、查询时间范围、结果是否完整以及不可用的数据源。某个数据源不可用时，最终回答不能表现为已经完成全部检查。

查询工具使用结构化结果状态：`complete` 表示本次结果完整，`partial` 表示仍有下一页；参数可由模型修正时返回 `invalid_input`，精确目标已经失效时返回 `not_found`，提案生成成功时返回 `approval_required`。外部依赖不可用直接结束工具调用，不伪装成空查询结果。

### 9.5 MCP 工具源

MCP 工具源在运维助手中独立管理，包括：

- 名称和地址
- 认证配置
- 允许导入的工具白名单
- 只读或允许写入
- 连接和工具发现状态
- 最近同步时间和失败原因

工具发现失败不能静默删除原有工具。系统保留上一次成功目录，同时把工具源标记为不可用；新任务应明确提示本次结论缺少该数据源。

## 10. 变更、审批与恢复

### 10.1 当前两段式变更

```text
用户提出变更
  -> Agent 查询当前同类资源
  -> 创建工具规范化并校验完整参数
  -> Eino StatefulInterrupt 保存 checkpoint
  -> Assistant 原子暂停 Execution、发布待审批项并释放 Worker 租约
  -> Console 展示完整创建参数
  -> 批准：同一 Execution 通过 ResumeWithParams 恢复原工具并调用 Admin API
  -> 拒绝：同一 Execution 恢复，工具返回拒绝结果，Agent 正常收尾
  -> 文字反馈：拒绝旧项并恢复同一 Execution，Agent 生成新的不可变审批项
  -> 持久化回答以及变更的成功、失败或结果不确定终态
```

模型可以调用创建工具，但第一次调用只能触发中断，不能直接调用审批接口。工具恢复上下文中的强类型 `ApprovalResult` 是唯一写入授权；聊天中的“确认”“直接执行”等自然语言不能构造这个结果。

提案一旦进入审批即不可修改。同一个 Execution 可以在用户反馈后顺序生成新提案，但同一时刻最多存在一个待审批项；旧项必须先进入 `rejected`。提案保存操作类型、完整规范化配置和脱敏摘要，不保存 API Key、证书私钥或模型工具原始输出。当前只创建新资源，没有待更新资源的版本；后续增加更新或删除时，必须在提案中绑定目标资源版本，并由 Admin API 在持久化写入时原子校验。

### 10.2 授权方式

当前只支持每次操作显式确认。完整授权模型的目标还包括：

- 当前会话内对特定工具授权
- 对特定资源范围预授权
- 定时任务按固定参数和资源范围预授权
- 高风险工具强制逐次确认
- 管理员全局禁用某类操作

只有实现预授权后才增加独立授权记录；届时必须包含发起人、授权范围、工具、参数约束、有效期和撤销状态。当前不能把一次批准扩展为会话级或资源级授权。

### 10.3 并发与幂等

审批接口在同一事务中更新提案状态，并把带中断 ID 和强类型决定的恢复命令写回原 Execution。MySQL 条件更新保证同一个中断只会排队恢复一次；重复批准、拒绝或提交反馈只返回当前状态。后台 Worker 领取后调用 Eino `ResumeWithParams`，不创建第二个 Execution。

Admin API 当前没有按客户端幂等键查询创建结果的协议。因此连接中断、超时、服务端错误或成功响应无法校验时，Assistant 无法证明资源是否已经创建，必须进入 `outcome_unknown` 并要求管理员先从资源列表核对。只有 Admin API 明确返回不会创建资源的校验、权限或冲突错误，才进入 `failed`。

Eino checkpoint 只保存模型—工具循环的暂停位置，不能替代业务状态。待审批配置、审批决定、Execution 状态和最终资源 ID 仍是独立的 MySQL 事实；Assistant 只有确认 checkpoint 已持久化后才发布审批项。Execution 完成或取消时删除 checkpoint。

当前提案状态固定为：

```text
pending_review -> executing -> succeeded
       |             |-------> failed
       |             `-------> outcome_unknown
       `-> rejected
```

`executing` 从批准成功排队开始，直到恢复的工具写入结果落库。执行失败、取消或 Worker 租约丢失时，如果系统无法证明 Admin API 没有接收请求，提案保守收敛为 `outcome_unknown`。该状态禁止自动重试。

稳定幂等键和按键查询执行结果仍是后续 Admin API 协议目标。实现之前不能用自动重试伪装幂等。

当前一次 Execution 只允许一个待审批项；用户反馈可以拒绝旧项并生成一项替代配置。未来支持多资源或跨系统变更时，应按有依赖关系的动作列表顺序执行，不宣称跨系统原子事务。某一步失败后停止后续动作，明确展示已成功、失败和未执行的部分；只有工具明确提供补偿操作且用户批准时才执行补偿，不生成未经定义的“自动回滚”。

外部 MCP 写工具也必须经过相同风险、审批和审计链路。只有声明幂等语义、结果查询方法和稳定版本的工具才能获得预授权；其他写工具只能逐次确认，超时后进入 `unknown`。

## 11. 记忆与知识

### 11.1 数据分类

| 类型 | 内容 | 生命周期 | 存储 |
| --- | --- | --- | --- |
| 页面上下文 | 当前页面、资源和筛选条件 | 单次请求 | 不持久化 |
| 工作记忆 | 当前步骤、工具结果和未完成事项 | 一次执行 | Eino 运行状态；中断时作为 checkpoint 写入 MySQL |
| 会话记忆 | 消息、上下文摘要和引用资源 | 可配置保留期 | MySQL |
| 执行检查点 | Agent 暂停位置 | Execution 完成、取消或删除 | MySQL |
| 业务恢复状态 | 待审批配置、审批决定和操作终态 | 按审计保留策略 | MySQL |
| 用户记忆 | 用户明确要求保存的偏好 | 直到修改或删除 | MySQL |
| 事件记忆 | 已确认的故障、证据、处理动作和结果 | 按保留策略 | MySQL |
| 产品知识 | 正式文档、操作手册和版本说明 | 随版本更新 | 文档检索工具 |

Gateway、Route、Service、Policy 当前配置和实时指标不是记忆。回答实时问题时必须重新调用工具获取。

历史事件记忆在检索结果中始终标记为历史信息。关联资源被删除、重新创建或 version 已变化时，记忆只能作为排障线索，不能作为当前事实。显式用户请求优先于会话指令，会话指令优先于长期偏好；不同用户的私有记忆默认互相不可见。

### 11.2 记忆写入

长期记忆不能直接从任意模型输出写入。写入流程为：

```text
发现候选内容
  -> 判断属于偏好、已确认事件还是普通对话
  -> 记录来源和关联资源
  -> 去重并设置有效期
  -> 需要时请求用户确认
  -> 写入长期记忆
```

用户偏好通过明确指令保存，例如“以后流量查询默认看最近一小时”。故障结论只有在存在工具证据且用户确认处理结果后，才能进入事件记忆。

每条长期记忆保存来源、创建人、创建时间、有效期和关联资源。Console 提供查看、修改、删除和禁用长期记忆的入口。

### 11.3 上下文压缩

上下文超过模型预算时生成结构化摘要。摘要必须保留：

- 用户当前目标和成功条件
- 已确认的假设
- 资源 ID 和 version
- 已执行工具及关键结果
- 不可用的数据源
- 待审批或未完成步骤

原始消息仍按保留策略存储在 MySQL。摘要只用于下一次模型调用，不覆盖审计记录。

### 11.4 语义检索

长期记忆优先使用结构化字段、全文搜索和资源关联查询。产品文档和外部知识通过独立检索工具提供。

当数据规模和召回场景证明需要向量检索时，由检索工具接入经过选择的向量存储；Assistant 核心数据模型不要求所有部署默认增加向量数据库。向量索引是派生数据，原始记忆和文档仍保存在各自事实来源中。

## 12. 持久化模型

MySQL 是 Assistant 业务状态和中断恢复数据的持久化来源。当前建立七张表：

| 数据集合 | 主要内容 |
| --- | --- |
| `assistant_model_connections` | 当前生效的单例模型连接；API Key 只写入、不回显 |
| `assistant_conversations` | 一个用户持续使用的对话容器，保存标题和最近活动时间 |
| `assistant_agent_executions` | 一次用户输入从接收到完成的生命周期，保存状态、模型、租约和错误分类 |
| `assistant_agent_execution_steps` | 一次 Execution 中已经发生的模型或工具步骤，保存顺序、状态和安全摘要 |
| `assistant_proposed_changes` | Agent 生成的不可变配置快照、审批状态、执行租约和最终资源 ID 或稳定错误码 |
| `assistant_agent_checkpoints` | Eino 序列化的暂停位置，与 Execution 同生命周期，不作为审批事实 |
| `assistant_messages` | 用户输入、助手最终回复及厂商显式返回的推理内容，分别关联会话及产生它的 Execution |

关系固定为：

```text
assistant_conversations    1 ── N assistant_agent_executions
assistant_conversations    1 ── N assistant_messages
assistant_agent_executions 1 ── N assistant_agent_execution_steps
assistant_agent_executions 1 ── N assistant_messages
assistant_agent_executions 1 ── N assistant_proposed_changes
assistant_agent_executions 1 ── 0..1 assistant_agent_checkpoints
```

Conversation 负责组织连续对话；Execution 负责表达一次回答是否仍在进行以及如何结束；Execution Step 记录模型和工具步骤；Message 保存可以重新展示的最终回答和显式推理内容；Proposed Change 独立表达一次审批与确定性写入；Checkpoint 只让 Eino 恢复同一个模型—工具循环。

Execution Step 与 Execution 在同一事务中收敛终态。Worker 成功、失败、取消或租约过期时，不会留下仍处于执行中的步骤。`summary` 只允许保存经过脱敏且可向用户展示的摘要，不保存模型请求、完整 Prompt、工具参数或原始工具输出。

流式文本分片不写入 MySQL，避免把传输过程混入业务事实。已保存的推理内容与最终回答隔离，既不作为后续模型请求的历史上下文，当前 Console 也不直接展示；界面只呈现可审计的执行步骤和最终回答。

当前使用 sqlc 生成类型安全的数据访问代码，并在手写事务中明确会话锁和 Execution 状态转换。这里不引入 GORM 或 Ent：当前模型很小，关键复杂度是并发约束和事务顺序，而不是对象映射。增加 ORM 会同时维护领域模型和 ORM 模型，但不会减少这些约束。

工具调用过程保存在 Execution Step；配置提案具有独立审批和执行生命周期，因此使用独立表。审批修改文字作为用户消息和一次性恢复命令保存，不建立重复的反馈模型。定时任务、长期记忆和工具源尚未形成产品闭环，当前不创建对应空表，也不把未来字段继续堆入现有表。

完整 Prompt、密钥、证书私钥、请求正文和未经筛选的工具原始输出不进入这些表。

Redis 只保存可以重建或会过期的状态：

- 一个 Execution 的流式事件
- SSE 断线恢复所需的事件 ID

Redis Stream 按 Execution 设置保留期，只用于短期重放。Redis 丢失不会丢失会话、最终消息、Execution 终态或等待审批的 checkpoint；Console 可以通过普通 HTTP 重新读取 MySQL 中的状态。

MySQL 不保存 Gateway 等声明式资源副本。Assistant 只保存审批时展示并执行的不可变配置快照，以及成功后的资源 ID；资源当前状态仍由 API Server 管理，回答实时问题时必须重新查询 Admin API。

## 13. API 与事件协议

当前 Console 使用普通 HTTP 管理模型连接、会话、Execution 和 Proposed Change，并使用 SSE 接收一次 Agent Execution 的流式事件。配置提案通过普通 HTTP 查询、批准、拒绝和提交修改反馈；三个决定都只把原 Execution 排队恢复，HTTP 请求本身不执行模型或 Admin API 调用。记忆、工具源和定时任务的 API 只在对应业务能力实现后增加。

当前 SSE 事件类型：

| 事件 | 含义 |
| --- | --- |
| `message.reasoning.delta` | 模型端点显式返回的推理内容增量 |
| `message.content.delta` | 助手最终回答增量 |
| `execution.started` | 本次请求开始执行 |
| `execution.completed` | 本次请求完成，携带最终消息 ID |
| `execution.failed` | 本次请求失败，携带稳定错误代码 |
| `execution.cancelled` | 本次请求已取消 |
| `execution.interrupted` | checkpoint 已保存，Execution 正在等待审批 |

事件协议只传递模型端点明确返回的结构化推理内容，不尝试获取模型内部隐藏思维链。未来如果增加工具执行通知，应使用独立的产品事件，例如“正在检查路由生效状态”，不能伪装成模型推理内容。

模型调用和工具调用过程保存在 Execution Step 中，通过普通 HTTP 查询，不为同一事实维护第二套 SSE 事件。审批状态同样以 MySQL 为事实来源；Console 提交决定后继续订阅同一个 Execution，直到出现新审批中断或最终状态。

断线重连使用 Execution ID 和 SSE `Last-Event-ID` 恢复。活动 Execution 的增量事件保存在 Redis 并设置保留期，任一 Assistant 实例都可以继续发送。Redis 状态已过期时，Console 通过普通 HTTP 获取 MySQL 中的 Execution 和消息，不保证逐 Token 重放。SSE 是单向协议，不额外设计客户端 ACK。

## 14. 定时任务与自动化

定时任务复用相同的 Agent、工具、记忆和审批体系，不建立另一套自动化执行框架。

每个任务包含：

- 名称和自然语言目标
- 固定调度表达式和时区
- 允许使用的 Agent 和工具
- 资源范围和参数约束
- 授权策略
- 最大步骤数、最长执行时间和失败重试策略
- 结果通知方式
- 启用状态和最近执行结果

自然语言目标描述每次运行需要达成的结果，但不能在运行时扩大权限。任务启用前必须生成并批准结构化执行边界，固定工具版本、输入 Schema、资源范围和参数约束；Agent 可以在该边界内根据实时证据选择查询步骤。相关工具发生不兼容升级、预授权过期或创建者权限被撤销时，任务自动停用并要求重新审批。

交互请求实例负责创建和管理任务。后台任务实例通过 MySQL 读取到期任务，并使用带 fencing version 的数据库租约保证同一任务只有一个有效执行者，不再叠加 Redis 分布式锁。定时表达式采用带时区的标准 cron 表达式；错过的执行默认不补跑，同一任务默认不并发，重试不会跨过下一次计划时间。这些默认值可以在创建任务时明确调整。

自动修复必须满足预授权范围，并设置单次最大修改数量、连续失败阈值和自动停用条件。超出范围时生成待审批事项，而不是继续执行。

## 15. 安全边界

### 15.1 身份与权限

当前单管理员部署中，Assistant 沿用 Console 登录身份。目标架构保留用户 ID、角色和权限字段，以便接入多用户后按实际身份调用 Admin API。

Assistant 使用自己的服务凭据访问 Admin API，但每次请求同时携带经过签名的用户身份和权限上下文。Admin API 仍然负责最终权限判断，不能只信任 Assistant 的工具选择结果。

身份委托使用短时签名令牌，至少绑定用户、目标服务、请求 ID、签发和过期时间，并防止重放。最终权限是服务身份权限、用户当前权限和预授权范围的交集；审批通过后如果用户权限或授权已撤销，执行仍必须拒绝。会话、记忆、审批和任务默认归创建用户所有，环境级共享必须由管理员显式授权。Ingate 仍只管理一个环境和配置域，不借此引入多租户资源隔离。

### 15.2 数据保护

- 密钥、证书私钥和模型凭据不进入模型上下文
- 请求 Header、查询参数和正文不因助手功能而新增持久化
- 工具输出先经过字段白名单、脱敏和大小限制
- 日志默认不记录用户原文、Prompt、完整工具参数和模型输出
- 对话和长期记忆提供保留期限与删除能力

### 15.3 Prompt 注入

工具返回内容和外部文档都视为不可信数据。系统指令明确禁止把数据内容中的命令当成新的系统规则。

外部 MCP 工具必须使用白名单。通用 Shell、任意 SQL、任意 HTTP 请求和动态代码执行不作为默认内置能力；如未来确有场景，需要独立的隔离环境、资源上限和更高等级审批。

MCP 地址由管理员配置并经过协议、主机和网络出口校验，禁止访问本机管理端口和云元数据地址；连接必须校验证书，认证信息只以密钥引用保存。外部内容只能填充工具声明允许的数据字段，不能修改工具白名单、审批对象或服务端风险判断。

## 16. 错误处理与结果完整性

工具错误需要保留两层信息：

- 内部错误包含真实原因、依赖服务和关联请求 ID，只在责任边界记录一次
- 用户错误说明哪项检查失败、对结论有什么影响以及可以如何恢复

最终回答应区分：

- 已由工具确认的事实
- 基于事实得出的判断
- 仍需验证的可能原因
- 未能访问的数据源

工具源、Analytics 或 Admin API 不可用时，Assistant 不能用已有数据生成一个没有限定条件的完整结论。

## 17. 可观测与审计

一次执行使用统一关联 ID 串联：

```text
conversation
  -> run
      -> model call
      -> agent delegation
      -> tool call
      -> approval
      -> Admin API operation
      -> final answer
```

运行指标包括：

- 请求量、成功率和端到端耗时
- 首字节时间和完整响应时间
- 模型调用量、Token、失败率和备用模型切换次数
- 工具调用次数、成功率、耗时和超时次数
- 审批通过、拒绝、过期和 version 冲突数量
- 定时任务积压、失败和自动停用数量
- Redis、MySQL 和外部 MCP 工具源健康状态

审计记录包含用户、目标资源、工具、参数摘要、审批、变更前后 version 和最终结果。审计不能依赖模型生成的自然语言摘要替代结构化字段。

## 18. 反馈与评测

Console 允许用户对回答标记有用、无用或结论错误，并对执行结果补充说明。反馈关联具体执行、模型版本、工具目录版本和 Prompt 版本。

项目维护固定评测集，至少覆盖：

- Route 未生效或引用无效
- 多个 Gateway 监听冲突
- Service 端点不可用或 TLS 配置错误
- 4xx、5xx 和延迟异常
- Caller 无权限或密钥失效
- 请求限流和 Token 额度耗尽
- 插件未安装、不可用或策略依赖冲突
- 数据源不可用导致结论不完整
- 配置变更审批、version 冲突和幂等重试

评测同时检查答案事实、证据引用、工具选择、权限边界和副作用。模型、Prompt、工具描述或专业 Agent 调整后必须运行相同评测集。

## 19. 可用性与扩展

Assistant 无法工作不能影响 Ingate 控制面和数据面。Console 应把助手不可用展示为独立能力故障，网关配置和流量转发继续正常运行。

交互实例保持无本地持久状态，可以水平扩展。Redis 保存短期流式事件，MySQL 保存持久业务状态。只要 Redis 保留期未过，SSE 重连后可以由任一实例继续发送；过期后按第 13 节返回执行快照。

后台任务与交互请求可以部署为同一实例，也可以使用同一二进制按角色拆分实例。角色拆分只为独立扩容和故障隔离，不产生新的产品组件或数据模型。

工具和专业 Agent 使用白名单注册。增加新工具不应修改根 Agent 主流程；增加专业 Agent 只需要声明职责、工具集合和委派描述。

## 20. 实现顺序

实现顺序不改变目标架构和数据模型：

1. 建立 Assistant 组件、模型连接、SSE 协议、会话持久化和内置查询工具（已完成）
2. 完成配置与流量诊断闭环，建立工具结果完整性（已完成；固定评测集待补充）
3. 增加创建 Gateway 和普通 HTTP Service 的提案、逐次审批、唯一执行权和结果不确定恢复（已完成）
4. 为更新与删除增加 version 校验，为 Admin API 增加稳定幂等键和执行结果查询
5. 增加专业 Agent，并把工具按领域收敛到独立白名单
6. 增加长期记忆管理、产品知识检索和用户反馈
7. 增加 MCP 工具源、定时巡检、预授权自动化和自动修复保护

每一步都必须形成可验收用户场景，不能添加没有调用方的接口、空实现或只为未来预留的持久化字段。

## 21. 参考实现

- [Dify Conversation / Message](https://github.com/langgenius/dify/blob/main/api/models/model.py)：会话负责组织连续对话，消息保存最终可展示内容；本项目不复制其面向工作流和计费的扩展字段
- [Open WebUI Chat / ChatMessage](https://github.com/open-webui/open-webui/tree/main/backend/open_webui/models)：对话与消息保持独立生命周期，消息只承载当前产品已经使用的状态和内容
- [LangGraph Threads and Runs](https://docs.langchain.com/langgraph-platform/assistants)：Thread 与 Run 分离，一次执行具有可独立查询的状态；本项目用 Conversation 和 Execution 表达同一边界
- [Eino ADK](https://github.com/cloudwego/eino/tree/main/adk)：Go Agent、AgentTool、中断和检查点
- [Google ADK Sessions](https://adk.dev/sessions/)：Session、State 和 Memory 的边界
- [Google ADK Memory](https://adk.dev/sessions/memory/)：跨会话记忆和检索接口
- [OpenAI Model and Tool Guidance](https://developers.openai.com/api/docs/guides/latest-model)：结构化工具调用、上下文延续和工具说明
- [Kagent Tools](https://github.com/kagent-dev/tools)：工具白名单、只读模式和 MCP 服务
- [HolmesGPT](https://github.com/HolmesGPT/holmesgpt)：运维诊断、工具结果和证据组织
