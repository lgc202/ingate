# Ingate AI 助手产品需求文档

## 文档状态

- 状态：已确认的完整产品目标
- 受众：产品、设计、Assistant、Console、Admin API 和安全治理开发者
- 范围：从对话理解、证据检索、计划与审批，到受控执行、验证、记忆和审计的完整运维助手
- 技术设计：[Assistant 技术规格](assistant-spec.md)
- 当前实现：[当前范围](../src/content/docs/reference/current-scope.md)与[运维助手运行说明](../src/content/docs/operations/assistant.md)

> 本文描述完整目标，不表示所有能力已经交付。当前实现只完成单进程后端骨架和依赖就绪检查；对话、Console、诊断、审批与执行按实施计划逐步交付。

## 1. 产品概述

Ingate AI 助手是嵌入现有 Console 的运维协作入口。它帮助平台工程师理解问题、收集有权限的组织知识和实时 Ingate 状态、形成可审阅计划，并在确定性的权限、风险与审批规则下执行有限变更。每个事实、判断、批准和副作用都必须可追溯。

它不是可以绕开控制面的万能机器人。Assistant 不参与业务流量，不替代 Admin API、API Server、Controller 或声明式资源，也不能让模型直接决定权限、风险或是否执行。所有变更仍通过目标 Ingate 的产品 API 进入既有 `Resource -> Compiler -> Delivery -> xDS -> Envoy` 链路。

产品采用“麻雀虽小，五脏俱全”的策略：默认以一个进程运行，首版不追求复杂部署和无限工具生态，但从第一条写入链路开始就具备持久任务、证据、幂等、风险、审批、验证、补偿、安全和审计闭环。

## 2. 目标

1. 让用户在一个持续会话中完成“描述目标—理解现状—审阅计划—批准变更—验证结果”。
2. 用带来源、版本、时间和权限范围的证据约束模型回答，明确区分事实、推断、未知和未找到。
3. 用模型之外的确定性代码约束工具、权限、风险、审批、幂等和网络访问。
4. 让任务在断线、服务重启、审批等待和依赖短暂故障后仍能恢复到正确位置。
5. 让用户和审计员能够还原每个动作为什么发生、由谁批准、实际产生了什么结果。
6. 复用现有 Console、身份和产品语言，以紧凑部署提供完整闭环，而不是建立第二套控制台和平台。

## 3. 用户与角色

| 角色 | 核心诉求 |
| --- | --- |
| 普通用户 | 发起只读咨询，查看自己有权访问的会话、回答和证据 |
| 平台工程师 | 诊断环境问题，审阅计划，发起受控动作并跟踪结果 |
| 审批人 | 在授权环境内查看完整差异和证据，批准或拒绝 R2 动作 |
| 安全管理员 | 参与 R3 双人审批，治理高风险动作和安全边界 |
| 安装管理员 | 登记 Ingate 环境，管理环境授权、工具与策略 |
| 知识管理员 | 管理组织知识来源、同步状态和权限标签 |
| 审计员 | 查询和导出经过脱敏的决策与执行链路 |

角色可以组合，但授权必须绑定具体环境范围。R3 的两个有效批准必须来自不同用户，并满足不同角色席位要求。

## 4. 用户故事

### US-001 持久且可恢复的对话

作为平台工程师，我希望在 Console 中提交目标并获得流式回答，以便不中断当前工作完成运维协作。

验收标准：

- 提交目标立即返回稳定任务 ID，不同步等待模型完成。
- 页面刷新后仍能看到用户消息、最终回答和任务状态。
- SSE 断线重连能补齐持久事件；临时 Token 丢失不影响最终答案。
- 使用同一幂等键重试不会创建第二个任务。

### US-002 有范围的身份与环境访问

作为安装管理员，我希望登记多个独立 Ingate 环境并按用户授予角色，以便一个 Assistant 安全服务多套 Ingate 安装。

验收标准：

- 用户只能发现和选择已授权环境，未授权请求不泄露环境是否存在。
- 每个会话、证据、计划、审批和动作都绑定环境。
- 长任务在每次工具调用和执行前重新检查当前权限。
- 环境凭证不进入模型、Workflow 历史、业务事件、日志或前端。

### US-003 权限过滤的组织知识

作为知识管理员，我希望导入带来源和权限标签的组织知识，以便 Assistant 在不越权的情况下复用团队经验。

验收标准：

- 知识源和文档具有明确同步状态、版本、来源、采集时间和权限标签。
- 权限过滤发生在内容进入模型之前，直接 ID、关键词和向量检索均不能绕过。
- 文档更新或删除后，权威数据和索引最终一致。
- 向量索引不可用时降级为权限过滤后的关键词检索。

### US-004 查询实时 Ingate 状态

作为平台工程师，我希望 Assistant 查询所选环境的 Gateway、Route 和 Service，以便回答基于当前配置而不是模型记忆。

验收标准：

- Agent 只能调用注册的只读工具，不能自行拼接地址或请求。
- 查询前后都校验用户、环境和资源权限。
- 查询失败明确区分未知、未找到、无权限和依赖不可用。
- 产品响应不暴露 Envoy、xDS、ext_proc 等实现概念。

### US-005 查看证据来源

作为用户，我希望每个关键事实都能打开来源详情，以便判断答案是否可靠和新鲜。

验收标准：

- 证据包含环境、对象身份、对象版本、采集时间、来源和可信级别。
- 过大内容保存为受权限保护的引用，模型只接收可追溯摘要。
- 无来源的模型推断不得展示为已确认事实。
- Console 只展示当前用户可见且经过脱敏的证据字段。

### US-006 审阅和修改结构化计划

作为平台工程师，我希望在执行前审阅计划并补充约束，以便确认影响、依赖和验证方式。

验收标准：

- 计划是最多 100 步的版本化 DAG，包含目标、依赖、工具、前置条件、影响和验证条件。
- 循环依赖、未知工具、非法输入或越权目标不能成为可执行计划。
- 修改计划创建新版本，旧版本保留只读记录并失效。
- 生成和修改计划本身不产生外部副作用。

### US-007 受预算约束的专业 Agent

作为平台工程师，我希望复杂问题按需使用专业角色，以便并行核对配置、知识和安全证据。

验收标准：

- 简单问题只使用 General Agent，复杂问题才启动专业角色。
- 单任务最多并行三个 Agent，每个角色最多八轮工具调用并有独立 Token 预算。
- 专业 Agent 只拥有角色允许的查询工具，不能执行变更。
- 角色结论冲突时由 Verifier 核对；无法消解的分歧明确展示给用户。

### US-008 获得证据化诊断

作为平台工程师，我希望诊断列出候选原因、置信度、证据和未知项，以便在行动前理解判断依据。

验收标准：

- 诊断结果必须通过封闭的结构化 Schema 校验。
- 每个事实性结论引用用户输入、知识片段或实时证据。
- 知识和实时状态冲突时同时展示两者，并优先采用更新的实时状态。
- 证据不足时等待输入或明确返回未知，不虚构资源、指标或结果。

### US-009 治理工具与策略

作为安装管理员，我希望查看和治理工具版本、输入约束、风险下限和启用状态，以便控制 Assistant 能做什么。

验收标准：

- 工具定义展示稳定名称、版本、类型、输入 Schema、风险下限和可恢复性。
- 未知、禁用或版本不匹配的工具不能进入新计划或执行。
- 工具或策略变更使用乐观并发并形成审计事件。
- 模型不能降低工具或管理员策略规定的风险下限。

### US-010 查看确定性风险

作为用户，我希望在执行前看到 R0–R3 风险及原因，以便理解是否以及为何需要审批。

验收标准：

- 风险由工具、动作、环境、资源、影响范围、可恢复性和策略确定性计算。
- 最终等级取所有来源的最高值，模型只能提供待验证属性，不能设置结果。
- 缺少必需风险属性时按 R3 或拒绝执行，不能默认放行。
- 风险结论绑定计划、动作、工具、环境和策略版本。

### US-011 允许的 R1 动作自动执行一次

作为平台工程师，我希望低风险且策略允许的非生产动作自动执行，以便减少不必要的审批等待。

验收标准：

- 首个 R1 场景是在非生产环境创建未被 Route 引用的 Service。
- 动作依次经过准备、预演、风险、前置检查、执行、核对和独立验证。
- 只有显式策略允许时才自动执行，并在写入前重新检查权限与环境版本。
- 重复请求、Workflow 重放或 Activity 重试都不会产生第二次副作用。

### US-012 R2/R3 分级审批

作为审批人或安全管理员，我希望高风险动作在绑定内容未变化的前提下获得所需批准，以便风险与责任清晰。

验收标准：

- R2 生产变更至少需要一名当前有权用户批准。
- R3 需要两个不同用户批准，其中至少一人是安全管理员或安装管理员。
- 批准、拒绝和要求修改均幂等；修改计划会生成新版本并使旧批准失效。
- 批准绑定 Task、Plan、Action、Tool、环境、资源、Policy 和过期时间，任一变化均失效。

### US-013 按 DAG 安全执行多步骤计划

作为平台工程师，我希望无依赖的安全步骤并行、有依赖的步骤按序执行，以便兼顾效率和正确性。

验收标准：

- 只有所有前置步骤成功后才调度下游动作。
- 单任务并行步骤不超过 20，等待审批只阻塞依赖分支。
- 每个动作有稳定 ID、幂等键和独立 attempt。
- 失败后仅继续计划明确允许的分支，不可达节点标记为跳过。

### US-014 验证失败后受控补偿

作为平台工程师，我希望动作成功但业务验证失败时得到受治理的补偿方案，以便安全恢复而不是隐式回滚。

验收标准：

- 验证通过独立读取或业务信号进行，不以 Execute 响应代替。
- 验证失败生成带原动作、目标状态和证据的补偿提案。
- 补偿重新经过准备、风险、权限和审批，不能因为名为回滚而绕过治理。
- 补偿成功显示“已恢复但原目标失败”，补偿失败保留两组失败证据。

### US-015 控制并恢复任务生命周期

作为用户，我希望暂停、恢复或取消长任务，并让任务跨进程重启恢复，以便安全应对变化。

验收标准：

- 暂停在安全边界生效，恢复回到原 DAG frontier 而不是从头重跑。
- 取消阻止新动作并取消支持取消的 Activity，但不伪装成撤销既有副作用。
- 审批等待、Timer、已完成动作和 attempt 在进程重启后保持一致。
- 恢复后重新校验权限、环境和策略。

### US-016 管理有作用域的长期记忆

作为用户，我希望明确确认、复用、编辑和删除长期记忆，以便 Assistant 记住可靠偏好而不擅自保存内容。

验收标准：

- 只有已完成任务中的已验证事实能够成为记忆候选，保存必须由用户明确确认。
- 保存前展示内容、来源、用途、作用域和敏感扫描结果。
- 个人记忆仅本人可见，组织记忆受组织和环境权限约束。
- 删除后新任务立即停止使用，并物理删除内容或销毁加密密钥及相关索引。

### US-017 查询并导出完整审计链

作为审计员，我希望查询和导出经过脱敏的完整决策链，以便复盘风险与责任。

验收标准：

- 可按时间、操作者、环境、任务、动作和结果过滤，并使用不透明 Cursor 分页。
- 目标、证据、计划、风险、审批、attempt、验证、补偿和未知结果按因果顺序关联。
- 产品 API 不能修改或删除审计事件，篡改可被摘要链发现。
- 导出异步生成、短期授权下载并应用与在线查询相同的权限和脱敏规则。

### US-018 安全处理注入与未知结果

作为安全管理员，我希望恶意内容不能扩大权限，写入超时也不会触发盲目重试，以便避免秘密泄漏和重复变更。

验收标准：

- 用户、知识和工具输出中的指令均不能改变系统规则、风险、权限或工具注册表。
- 工具不能访问未登记地址、执行任意命令或读取凭证值给模型。
- 写入结果不确定时进入 `UNKNOWN`，先用同版本工具核对而不是重试 Execute。
- 无法核对时任务安全暂停，并展示已知事实、未知范围和人工建议。

### US-019 完整运维旅程

作为平台工程师，我希望完成一次有真实证据的诊断、规划、审批、执行和验证，以便确认 Assistant 可以承担受控运维工作。

验收标准：

- 同一旅程包含知识与实时证据、R0/R1/R2 DAG、授权审批和独立验证。
- R1/R2 动作均恰好执行一次，R2 在审批前没有写请求。
- Console 能连续查看诊断、证据、计划、风险、审批、动作、验证和摘要。
- 可执行验收流程同时覆盖幂等重试、审批过期、`UNKNOWN` 核对和秘密泄漏检查。

## 5. 功能需求

### 5.1 会话、任务与流式交互

- **FR-1**：系统必须把会话及其消息持久化到 MySQL，并按当前用户和环境授权读取。
- **FR-2**：系统必须把每次需要异步处理的用户目标建模为具有稳定 ID 和显式生命周期的 Task。
- **FR-3**：系统必须接受长度为 1–20,000 字符的用户目标，并在开始模型处理前持久化原始消息。
- **FR-4**：系统必须在 Temporal Activity 内运行 Agent，Temporal Workflow 不得直接调用模型、网络或数据库。
- **FR-5**：系统必须用用户、会话和幂等键去重消息提交与任务控制命令。
- **FR-6**：系统必须持久化最终回答、结构化结果与安全错误，使页面刷新后可恢复。
- **FR-7**：系统必须通过 SSE 同时传输不落业务库的临时 Token 增量和带单调序号的持久任务事件。
- **FR-8**：系统必须根据 `Last-Event-ID` 补齐持久事件，并允许任务在连接中断或进程重启后继续。

### 5.2 知识、实时状态与证据

- **FR-9**：系统必须支持创建知识源、导入文档并展示 `pending`、`running`、`succeeded` 或 `failed` 同步状态。
- **FR-10**：系统必须通过注册的只读工具查询已授权 Ingate 环境中的 Gateway、Route、Service 及其关系。
- **FR-11**：系统必须把用户输入、知识和实时查询统一为包含来源、版本、采集时间、环境与可信级别的 Evidence。
- **FR-12**：系统必须在内容进入检索结果和模型上下文前应用用户、组织、环境与文档权限过滤。
- **FR-13**：系统必须保存知识来源的外部标识和版本，并让更新与删除最终同步到全文和向量索引。
- **FR-14**：系统必须把 MySQL 作为知识事实来源，并在 Qdrant 不可用时降级为受权限约束的关键词检索。
- **FR-15**：系统必须把超出模型输入限制的工具或知识内容保存为受保护引用，只向模型提供有界摘要。
- **FR-16**：系统必须区分未知、未找到、无权限和依赖失败，并在知识与实时状态冲突时展示冲突且优先实时状态。

### 5.3 计划与多 Agent

- **FR-17**：系统必须把计划保存为包含稳定 ID、递增版本、目标环境、步骤、依赖、动作提案和验证条件的 DAG。
- **FR-18**：系统必须在计划生效前拒绝循环依赖、超过 100 步、未知工具、非法 Schema、越权目标或缺少验证的动作。
- **FR-19**：系统必须让用户审阅并要求修改计划，任何修改创建新版本并使旧风险结论和批准失效。
- **FR-20**：系统必须提供 General、Planner、Researcher、Diagnostician、SecurityReviewer 和 Verifier 六种角色配置。
- **FR-21**：系统必须只在复杂任务中用 Temporal Child Workflow 启动专业 Agent，并要求其返回结构化结果。
- **FR-22**：系统必须把单任务同时运行的 Agent 数量限制为最多三个。
- **FR-23**：系统必须把每个 Agent 的工具调用限制为最多八轮，并执行独立 Token 和时间预算。
- **FR-24**：系统必须保留成功的子 Agent 结果，在分支失败时明确降级，并由 Verifier 处理相互冲突的结论。

### 5.4 工具与执行

- **FR-25**：系统必须为每个工具保存稳定名称、不可变版本、类型、输入输出 Schema、风险下限、可恢复性和启用状态。
- **FR-26**：系统必须只从服务端工具注册表解析调用，拒绝未知、禁用、版本不匹配或输入不合法的工具。
- **FR-27**：系统必须在 Agent 角色、用户角色、环境范围和资源权限的交集中计算可用工具。
- **FR-28**：系统必须对工具和策略变更使用版本并发控制并记录审计，模型不得修改治理配置。
- **FR-29**：系统必须给每个动作分配稳定 ID、幂等键和独立 attempt，并在外部写入前持久化最小审计事实。
- **FR-30**：系统必须让动作依次经过 Prepare、Dry Run、Risk Decision、Preconditions、Execute、Inspect 和 Verify 阶段。
- **FR-31**：系统必须仅在 DAG 依赖满足时调度动作，并把单任务并行步骤限制为最多 20。
- **FR-32**：系统必须在重试、重放、暂停、恢复、取消和 Worker 重启时保持已完成动作不重复执行。

### 5.5 风险与审批

- **FR-33**：系统必须依据工具下限、动作类型、环境敏感度、资源敏感度、影响范围、可恢复性和策略计算 R0–R3 风险。
- **FR-34**：系统必须取所有风险来源中的最高等级；必需属性未知时按 R3 或拒绝执行。
- **FR-35**：系统必须展示风险等级、决定因素、审批要求和可恢复性，并将结论绑定计划、动作、工具、环境与策略版本。
- **FR-36**：系统必须只在非生产、可恢复、前置条件成立且策略显式允许时自动执行 R1，并在执行前重新校验权限和绑定内容。
- **FR-37**：系统必须要求 R2 动作在执行前获得一名对目标环境有审批权限的用户批准。
- **FR-38**：系统必须要求 R3 动作获得两个不同用户批准，其中至少一人是安全管理员或安装管理员。
- **FR-39**：系统必须支持批准、拒绝和要求修改，并对 R3 决定应用最长 15 分钟的有效期。
- **FR-40**：系统必须在批准和执行时重新校验发起人、审批人、环境和资源权限，并对未授权对象隐藏存在性。
- **FR-41**：系统必须把批准绑定 Task、Plan 版本、Action Digest、Tool 版本、环境修订、资源版本、Policy 版本和过期时间。
- **FR-42**：系统必须让审批决定幂等且并发安全，任一绑定值变化后自动失效并阻止旧动作执行。

### 5.6 验证、补偿与未知结果

- **FR-43**：系统必须通过独立读取或业务信号验证动作结果，不得以 Execute 响应作为最终成功证据。
- **FR-44**：系统必须把用户断言、资源版本和预期业务条件保存为计划绑定的版本化验证条件。
- **FR-45**：系统必须在验证失败时生成包含原动作、目标状态和失败证据的显式补偿提案。
- **FR-46**：系统必须让补偿动作重新经过准备、风险、权限和审批，不得执行隐式回滚。
- **FR-47**：系统必须在补偿成功后区分“已恢复但原目标失败”，补偿失败时同时保留原始与补偿证据。
- **FR-48**：系统必须把可能已产生副作用的超时或连接中断标记为 `UNKNOWN`，先 Inspect，再依据确定结果、幂等声明和策略决定继续或暂停。

### 5.7 记忆与审计

- **FR-49**：系统必须只从完成任务中的已验证事实提出记忆候选，并在用户明确确认前禁止持久保存。
- **FR-50**：系统必须让记忆绑定个人或组织作用域，并在保存、检索和使用时应用相应权限。
- **FR-51**：系统必须记录记忆来源、版本和每次进入模型上下文的 usage，并在回答中展示来源。
- **FR-52**：系统必须在保存前拒绝秘密和敏感请求，并在删除时物理删除或销毁密钥且移除所有索引。
- **FR-53**：系统必须以只追加审计事件关联目标、证据、计划、风险、审批、attempt、验证、补偿和未知结果。
- **FR-54**：系统必须为关键审计事件生成可验证的防篡改摘要链，且产品 API 不提供修改或删除能力。
- **FR-55**：系统必须支持按时间、操作者、环境、任务、动作和结果过滤审计事件，并使用不透明 Cursor 分页。
- **FR-56**：系统必须异步生成经过授权和脱敏的短期审计导出；关键审计写入失败时变更动作必须 fail closed。

### 5.8 产品与安全边界

- **FR-57**：系统必须复用现有 Console 的应用 Shell、导航和登录身份，不得建立独立前端或第二套登录。
- **FR-58**：系统必须允许一个 Assistant 登记多套独立 Ingate 环境，同时保持每套 Ingate 仍代表一个环境和配置域。
- **FR-59**：系统必须按最小权限过滤环境、证据、工具、任务和审计数据，并在长任务的每次外部访问前重新授权。
- **FR-60**：系统必须只在查询或动作边界短期解析凭证引用，其他层和持久化记录不得接触凭证值。
- **FR-61**：系统必须把用户输入、知识和工具输出视为带来源的不可信数据，禁止它们改变系统指令、权限、风险和工具注册表。
- **FR-62**：系统必须将出站网络限制在管理员登记的模型、知识和 Ingate 地址，禁止任意 URL、命令和未注册连接。
- **FR-63**：系统必须对日志、错误、SSE、模型上下文、审计查询和导出应用一致的秘密与敏感字段清洗规则。
- **FR-64**：系统必须隔离 Assistant 故障对配置管理和业务流量的影响，并在产品 API 与页面中隐藏 Temporal、Eino、Envoy 和 xDS 等实现细节。

## 6. 非目标

- 不让 Assistant 成为声明式资源或当前有效配置的事实来源。
- 不允许模型直接访问 etcd、Controller、Envoy、数据库、Shell 或任意网络地址。
- 不替代 Admin API 的产品校验、API Server 的资源持久化或 Controller 的发布判断。
- 首版不提供用户自定义 MCP、任意插件代码或通用互联网浏览能力。
- 首版不提供独立前端、独立账号体系或独立登录入口。
- 首版不把请求 Header、Cookie、Authorization、完整请求正文或凭证保存为知识、记忆或审计内容。
- 首版不提供定时无人值守变更；R2/R3 不因自动化策略绕过人工批准。
- 首版不拆分 API、Worker 和后台组件为 Kubernetes 多角色部署，也不交付 Helm Chart。
- 不为旧 Assistant API、Redis Stream、进程内状态机或旧数据表提供兼容层与迁移层。
- 不承诺模型永远正确；产品保证的是证据、边界、可解释性和安全失败方式。

## 7. 设计考虑

Assistant 作为现有 Console 的一级能力出现，复用相同的侧边导航、页面框架、颜色、字体和身份上下文。主页面以会话为中心，但不能退化成只有聊天气泡的界面。

每个任务至少包含以下可查看区域：

- 对话与当前状态；
- 证据及其来源、时间和可信级别；
- 结构化计划、依赖和版本；
- 风险原因、影响、审批席位和失效原因；
- 动作阶段、attempt、验证和补偿；
- 最终摘要与审计入口。

高风险动作必须使用明确的确认文案和差异展示。页面使用 Gateway、Route、Service 等产品概念，不向用户暴露 Workflow、Activity、Eino、xDS、ext_proc 等内部名词。等待、未知、已恢复和失败必须具有不同视觉语义，不能都归为模糊的“处理中”或“异常”。

## 8. 技术考虑

- Assistant 默认以一个 `ingate-assistant --role=all` 进程承载 Kratos HTTP、Temporal Worker 和必要后台组件。
- MySQL 是会话、业务状态、治理配置、证据、记忆和审计的权威数据源；Temporal 是持久工作流编排器。
- Eino 只用于 Agent 包内的模型与工具循环，Eino 类型不能进入 API、业务、Workflow 或工具契约；首版不同时引入 LangChainGo。
- Qdrant 是可选向量索引，故障时降级为 MySQL 权限过滤后的关键词检索。
- 所有 Ingate 查询与动作都通过版本化工具调用目标 Admin API，不直接访问 API Server 或数据平面。
- API 写请求使用幂等键和版本条件；MySQL 与 Temporal 之间通过 Outbox 和 Reconciler 收敛。
- SSE 的 Token 增量是临时体验数据，持久状态事件和最终消息才是可恢复事实。
- 具体架构、接口、状态、数据表和错误契约见[技术规格](assistant-spec.md)。

## 9. 成功指标

以下指标用于首个完整版本验收，不替代上线后的容量基线：

- 完整验收旅程能够从 Console 完成诊断、计划、R1、R2、验证和审计，不需要直接操作数据库或 Temporal。
- 在消息重复、SSE 重连、Activity 重试和 Worker 重启场景下，任务与外部副作用重复率为 0。
- R2/R3 动作在有效审批前产生外部写请求的次数为 0。
- 所有事实性诊断结论具有可访问证据，无法提供证据的内容明确标记为推断或未知。
- 撤权后发生的新工具访问、知识命中或动作执行次数为 0。
- 注入验证中，风险降级、未注册工具调用、未允许网络访问和明文秘密泄漏次数均为 0。
- 写入结果不确定时，盲目重试 Execute 的次数为 0。
- Assistant 停止或依赖不可用时，Ingate 配置管理和 Envoy 业务流量保持可用。
- 90% 的只读问答无需专业 Agent；复杂任务始终遵守三 Agent、八工具轮次和配置 Token 预算。
- 审计员能够从任一已执行动作追溯到发起目标、证据、计划、风险、批准、attempt 和验证结果。

## 10. 开放问题与延期决策

当前没有阻塞实施的产品问题。以下事项已有明确边界，后续只有出现真实需求时才重新设计：

| 事项 | 当前决策 |
| --- | --- |
| Console 交付顺序 | 完整产品必须共用 Console；当前后端骨架阶段允许暂缓页面实现 |
| Agent 框架 | 首版使用 Eino，限制在 Agent 包内；不同时引入 LangChainGo |
| 数据库 | 使用 MySQL 作为业务事实来源，不沿用旧数据模型 |
| 向量数据库 | Qdrant 可选，不能成为权限或内容事实来源 |
| 多实例与角色拆分 | 首版只支持紧凑单进程；Kubernetes 分角色部署延期 |
| 用户自定义工具 | 首版只允许服务端注册的版本化工具；用户自定义 MCP 延期 |
| 完整 E2E | 保留为第 22 个实施阶段，按既定排期延后但不从目标中删除 |
