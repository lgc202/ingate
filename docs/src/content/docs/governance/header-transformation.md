---
title: 请求响应转换
description: 按顺序修改 Route 的请求与响应 Header
---

请求响应转换用于在不修改业务服务的情况下删除、重命名或写入 HTTP Header。当前策略只应用到 Route，并由标准请求响应转换插件执行。

## 前置条件

进入 **治理与扩展 → 插件**，确认“请求响应转换”已经安装且状态为“已生效”。如果插件市场没有该插件，先检查已启用插件源的同步状态和目录内容。

插件未安装时，Console 会禁用该策略的创建入口；已有策略也不会绕过插件依赖直接生效。

## 创建策略

1. 进入 **治理与扩展 → 策略**。
2. 选择 **创建策略 → 请求响应转换**。
3. 填写策略名称并选择一个或多个 Route。
4. 按实际处理顺序添加请求或响应规则。
5. 保存并等待策略及目标状态变为“已生效”。

策略可以先不选择 Route。此时配置会保存为“未应用”，不会改变流量。

## 规则语义

| 操作 | 结果 |
| --- | --- |
| 删除 Header | 删除全部同名值 |
| 重命名 Header | 把原名称下的值移动到新名称 |
| 替换 Header | 删除同名旧值，再写入新值 |
| 添加 Header | 仅在 Header 不存在时写入；已有同名值保持不变 |
| 追加 Header | 始终新增一个同名值；Header 不存在时直接创建 |

Header 名称不区分大小写。规则按 Console 中的列表顺序执行，因此后续规则看到的是前面规则处理后的结果。请求规则在转发到 Service 前执行，响应规则在返回客户端前执行。

## 选择作用范围

策略直接引用 Route。需要让一个 Gateway 下的所有流量都执行相同转换时，应明确选择该 Gateway 下的每条 Route；新增 Route 不会自动继承已有策略。

多条请求响应转换策略可以命中同一 Route，Controller 会按稳定顺序组合执行。若转换顺序会影响结果，优先把相关规则放入同一策略，避免依赖多条策略之间的顺序表达业务逻辑。

## 验证

保存后先确认策略目标状态为“已生效”，再向目标 Route 发起请求。例如添加响应 Header `x-ingate-policy: enabled` 后：

```bash
curl -i http://127.0.0.1:8080/example
```

响应中应出现配置的 Header。若状态为“异常”，先检查插件是否已安装并可用；若状态持续“发布中”，再检查同一配置域中的其他异常资源。
