# PRD：Ingate 只读运维助手

## 1. 产品概述

Ingate 只读运维助手帮助管理员排查当前配置域内的 Gateway、Route 和 Service 问题。

用户可以在现有 Console 中提问，例如：

> 为什么 Route `checkout-api` 一直没有生效？

助手根据当前 Ingate 的真实资源状态和随版本发布的产品文档，自主选择只读能力进行检查，最终提供：

- 诊断结论；
- 支撑结论的资源和文档依据；
- 已执行的只读检查；
- 建议用户检查或修改的配置；
- 证据不足时明确说明无法确定。

首版助手不创建、修改、删除或发布资源，不执行命令，也不参与业务流量和配置发布。

管理员通过 Console 配置 Assistant 使用的模型连接。首版同时支持直连 OpenAI-compatible 模型端点，以及通过 Ingate Gateway、AI Route 和 Model Service 调用模型；模型连接不写入进程配置文件。

### 核心产品概念

- **会话**：围绕一个问题持续进行的对话。
- **运行**：用户提交一次问题后，助手完成的一次处理过程。
- **内容项**：运行过程中形成的用户消息、助手回答、工具活动、依据或失败结果。
- **模型连接**：当前 Ingate 内共享的一份 Assistant 模型调用配置，可以选择直连或经 Ingate 调用。

只有完成后的、有明确语义的内容项需要保留。流式 token、内部推理和底层框架事件不属于用户历史记录。

## 2. 目标

- 完成 Gateway、Route 和 Service 配置及生效状态的排障闭环。
- 让用户看到助手进行了哪些有意义的只读检查。
- 让资源和产品规则相关结论可以追溯到依据。
- 在页面刷新或服务重启后保留已经完成的对话内容。
- 在运行失败后提供简单、明确的重试能力。
- 在现有 Console 中提供统一的使用体验。
- 允许管理员通过 Console 配置、查看和切换 Assistant 的模型连接。
- 同时支持直连 OpenAI-compatible 模型，以及通过 Ingate AI Route 调用模型。
- 保持产品协议与模型、Agent 框架及内部编排方式解耦。
- 为后续增加只读工具或专门 Agent 保留自然扩展空间，但不预先实现这些能力。

## 3. 用户故事

### US-001：创建和查看排障会话

**Description:** 作为 Ingate 管理员，我希望创建并重新打开排障会话，以便持续查看问题上下文和历史结论。

**Acceptance Criteria:**

- [ ] Console 用户可以创建新会话。
- [ ] 用户可以查看当前 Ingate 中的会话列表。
- [ ] 用户可以打开一个会话。
- [ ] 会话内容按照产生顺序展示。
- [ ] 页面刷新后，已经完成的内容仍然存在。
- [ ] Assistant 服务重启后，已经完成的内容仍然存在。
- [ ] 会话只属于当前 Ingate，不出现环境选择。
- [ ] 不从其他会话自动注入用户画像或长期记忆。

### US-002：提交问题并观察运行状态

**Description:** 作为 Ingate 管理员，我希望提交问题并实时观察处理状态，以便知道助手是否仍在工作。

**Acceptance Criteria:**

- [ ] 系统拒绝空白问题。
- [ ] 有效问题提交后立即出现在当前会话。
- [ ] 每次提交产生一次独立运行。
- [ ] 页面可以区分运行中、已完成和失败状态。
- [ ] 助手回答以流式方式逐步展示。
- [ ] 流式 token 不作为独立历史内容保存。
- [ ] 运行完成后，重新打开会话可以看到完整回答。
- [ ] 用户不需要选择模型、工具或 Agent。

### US-003：查看助手执行的只读检查

**Description:** 作为 Ingate 管理员，我希望看到助手检查了哪些资源和文档，以便理解结论从何而来。

**Acceptance Criteria:**

- [ ] 助手读取资源或搜索文档时，页面显示对应的工具活动。
- [ ] 工具活动使用 Gateway、Route、Service 和产品文档等用户可理解的名称。
- [ ] 工具活动可以区分进行中、成功和失败。
- [ ] 成功活动展示经过裁剪的结果摘要，而不是完整原始响应。
- [ ] 工具活动完成后随会话一起保存。
- [ ] 重新打开会话时可以查看已经完成的工具活动。
- [ ] 页面不展示模型思维链、内部提示词或框架事件。
- [ ] 页面不展示凭据、敏感配置或内部错误详情。

### US-004：检查当前资源状态

**Description:** 作为 Ingate 管理员，我希望助手检查真实的 Gateway、Route 和 Service，以便诊断结果与当前系统一致。

**Acceptance Criteria:**

- [ ] 助手可以按用户提供的名称或 ID 定位 Gateway、Route 和 Service。
- [ ] 助手可以读取资源的产品配置、当前版本和生效状态。
- [ ] 助手可以识别 Route 引用的 Gateway 和 Service。
- [ ] 资源依据包含资源类型、资源 ID、读取版本和读取时间。
- [ ] 找不到目标资源时，助手明确说明未找到的对象。
- [ ] 现有只读能力无法核实原因时，助手明确说明能力边界。
- [ ] 资源访问失败时，助手不得把未知状态描述为正常或异常。
- [ ] 助手不具备任何资源写入能力。

### US-005：查询当前版本产品文档

**Description:** 作为 Ingate 管理员，我希望助手查询与当前版本一致的产品文档，以便理解配置规则和状态含义。

**Acceptance Criteria:**

- [ ] 助手只能查询随当前 Ingate 版本发布的受控文档。
- [ ] 文档依据包含文档标题、路径和相关章节。
- [ ] 页面可以区分资源依据和文档依据。
- [ ] 找不到适用文档时，助手明确说明没有找到相关文档。
- [ ] 首版不使用互联网搜索补充回答。
- [ ] 首版不提供文档上传或知识库导入入口。

### US-006：获得有依据的诊断建议

**Description:** 作为 Ingate 管理员，我希望获得清晰且可核验的诊断建议，以便自行决定如何处理问题。

**Acceptance Criteria:**

- [ ] 对 Route 未生效问题，助手检查目标 Route 及其引用的 Gateway 和 Service。
- [ ] 回答包含结论、依据、建议和限制。
- [ ] 配置和状态事实可以定位到资源依据。
- [ ] 产品规则可以定位到文档依据。
- [ ] 回答明确区分已观察到的事实和助手推断。
- [ ] 证据不足或证据冲突时，回答明确标记为无法确定。
- [ ] 建议使用 Gateway、Route 和 Service 等产品术语。
- [ ] 回答不暴露 xDS、Envoy filter、ext_proc 等内部实现。
- [ ] 建议只描述用户可以检查或修改的内容。
- [ ] 页面不提供执行、应用或自动修复入口。

### US-007：处理失败并重新运行

**Description:** 作为 Ingate 管理员，我希望失败后能够重新运行原问题，以便从临时故障中恢复。

**Acceptance Criteria:**

- [ ] 模型或只读依赖不可用时，本次运行显示为失败。
- [ ] 失败信息不包含内部错误、凭据或完整模型请求。
- [ ] 失败前已经完成的用户可见内容保持可查看。
- [ ] 用户可以基于原问题发起一次新的运行。
- [ ] 重试不会覆盖或修改原失败记录。
- [ ] 新运行可以产生新的工具活动和回答。
- [ ] 系统不声称恢复了已经丢失的流式 token。
- [ ] 首版不要求从中断位置继续执行。

### US-008：在现有 Console 中使用助手

**Description:** 作为 Ingate 管理员，我希望在现有 Console 中完成排障，以便不需要使用独立系统或重复登录。

**Acceptance Criteria:**

- [ ] Assistant 页面复用现有 Console 外壳和访问入口。
- [ ] 页面包含会话列表、当前会话内容和问题输入区域。
- [ ] 用户消息、助手回答和工具活动具有明确的视觉区别。
- [ ] 工具活动和依据可以按需展开。
- [ ] 流式回答生成期间保持可读。
- [ ] 页面不包含环境切换、审批或变更执行控件。
- [ ] Assistant 不可用时，Console 其他功能仍可访问。
- [ ] 在浏览器中验证创建会话、提交问题、查看检查过程、查看依据和刷新恢复。

### US-009：端到端验证核心排障流程

**Description:** 作为维护者，我希望通过可重复的端到端验证覆盖完整排障流程，以便发现跨组件回归。

**Acceptance Criteria:**

- [ ] 自动化 API 端到端验证创建具有明确引用关系和状态的 Gateway、Route 和 Service。
- [ ] 验证创建会话、提交问题、产生运行和接收流式回答的完整流程。
- [ ] 验证运行过程中产生用户可见的只读工具活动。
- [ ] 验证最终回答包含资源依据和文档依据。
- [ ] 验证重新读取会话可以恢复完成后的内容项。
- [ ] 验证 Assistant 重启后，完成后的内容仍然存在。
- [ ] 覆盖资源不可访问或模型生成失败的路径。
- [ ] 验证失败运行可以重新发起。
- [ ] 失败响应不包含内部错误、凭据或完整模型请求。
- [ ] 验证使用确定性的模型替代能力，不依赖真实模型输出的随机性。
- [ ] 验证可以通过一个命令重复执行并接入 CI。
- [ ] 验证自行准备和清理所需数据。
- [ ] Console 完整流程按照仓库约定通过浏览器验证，不新增前端自动化测试。

### US-010：配置 Assistant 模型连接

**Description:** 作为 Ingate 管理员，我希望在 Console 中配置 Assistant 使用的模型连接，以便在直连模型和经 Ingate 调用之间选择，而不修改服务配置文件。

**Acceptance Criteria:**

- [ ] 用户可以查看当前 Ingate 共享的模型连接配置。
- [ ] 用户可以选择直连 OpenAI-compatible 模型端点。
- [ ] 直连模式可以配置基础地址、模型名和可选 API Key。
- [ ] 用户可以选择通过 Ingate Gateway 和 AI Route 调用模型。
- [ ] Ingate 模式可以配置可访问的 Gateway 基础地址，并选择 Gateway、AI Route 和该 Route 发布的逻辑模型。
- [ ] Ingate 模式可以配置受保护 Route 使用的可选 Caller Access Key。
- [ ] 系统在保存 Ingate 模式前校验 Gateway、Route 和逻辑模型之间的引用关系。
- [ ] 读取配置时只返回凭据是否已经配置，不返回 API Key 或 Caller Access Key。
- [ ] 同一种模式更新时，未提供凭据表示保留已有凭据，显式清除表示删除凭据。
- [ ] 切换模式时不复用旧模式的凭据。
- [ ] 模型连接变更只影响变更后开始的运行，不改变正在进行或已经完成的运行。
- [ ] 未配置模型连接时仍可查看会话历史，但不能开始新的运行。
- [ ] 模型连接属于当前 Ingate，不按用户或会话分别保存。

## 4. 功能需求

- FR-1：系统必须通过现有 Console 提供访问入口。
- FR-2：系统必须将当前 Ingate 作为唯一配置域。
- FR-3：系统必须允许用户创建会话。
- FR-4：系统必须允许用户列出当前 Ingate 中的会话。
- FR-5：系统必须允许用户打开一个会话。
- FR-6：系统必须按照产生顺序返回会话内容。
- FR-7：系统必须拒绝空白问题。
- FR-8：系统必须为每次有效提问创建一次独立运行。
- FR-9：系统必须流式返回运行状态和回答内容。
- FR-10：系统必须保存完成后的用户消息。
- FR-11：系统必须保存完成后的助手回答。
- FR-12：系统必须保存完成后的工具活动摘要。
- FR-13：系统必须保存回答引用的来源。
- FR-14：系统不得把流式 token 作为独立历史记录保存。
- FR-15：系统必须向用户展示有意义的只读工具活动。
- FR-16：系统不得向用户展示模型内部推理。
- FR-17：系统必须只读访问 Gateway、Route 和 Service。
- FR-18：系统必须能够识别 Route 引用的 Gateway。
- FR-19：系统必须能够识别 Route 引用的 Service。
- FR-20：系统必须为资源事实提供资源依据。
- FR-21：系统必须为产品规则提供文档依据。
- FR-22：系统必须区分事实、推断和无法确定的内容。
- FR-23：系统必须允许用户重新运行失败的问题。
- FR-24：系统不得覆盖失败运行的历史记录。
- FR-25：系统不得向 Agent 提供资源写入能力。
- FR-26：系统不得提供变更执行接口。
- FR-27：系统不得返回或记录敏感信息和完整模型请求。
- FR-28：系统不得向公共协议暴露模型或 Agent 框架。
- FR-29：Assistant 故障不得阻塞配置管理和发布。
- FR-30：Assistant 故障不得影响经过 Envoy 的业务流量。
- FR-31：系统必须通过 Assistant API 读取和更新当前 Ingate 共享的模型连接。
- FR-32：系统必须支持直连 OpenAI-compatible 模型端点。
- FR-33：系统必须支持通过 Ingate Gateway 和 AI Route 调用模型。
- FR-34：系统不得从启动配置文件或环境变量读取模型选择。
- FR-35：系统必须在直连模式保存基础地址、模型名和可选 API Key。
- FR-36：系统必须在 Ingate 模式保存 Gateway 基础地址、Gateway ID、Route ID、逻辑模型名和可选 Caller Access Key。
- FR-37：系统必须在保存 Ingate 模式前验证所选 Route 是引用所选 Gateway 的 AI Route，并且发布所选逻辑模型。
- FR-38：系统必须把模型凭据作为只写字段处理，读取 API、日志和错误均不得返回明文。
- FR-39：系统必须允许保留、替换和显式清除当前模式的凭据。
- FR-40：系统必须在切换连接模式时删除旧模式凭据。
- FR-41：系统必须让一次运行使用启动时读取的模型连接快照。
- FR-42：系统必须在未配置模型连接时拒绝新运行，同时保持历史查询可用。

## 5. 非目标

首版不包含：

- 创建、修改、删除或发布 Ingate 资源；
- 自动修复和命令执行；
- 人工审批；
- 风险分级；
- DAG 任务编排；
- 回滚和补偿；
- 中断位置恢复和流式事件重放；
- 多 Agent 协作界面；
- 多 Ingate 环境管理；
- Assistant 独立认证、用户授权和会话隔离；
- 跨会话长期记忆和用户画像；
- 用户知识库导入；
- 互联网搜索；
- 同时保存或自动选择多个 Assistant 模型连接；
- 直连非 OpenAI-compatible 模型协议；
- 向浏览器返回已经保存的模型凭据；
- 用户自定义 MCP 或其他工具；
- 定时任务和自动巡检；
- 通用日志与流量根因分析平台；
- 与 Ingate 运维无关的通用聊天。

这些能力需要在确认真实需求后分别建立 PRD。首版不为它们增加占位页面、接口、数据库字段或空实现。

## 6. 设计考虑

- Assistant 页面属于现有 Console，不创建独立前端和登录入口。
- 模型连接由 Console 调用 Assistant API 配置，不要求用户修改 YAML 或重启 Assistant。
- 直连和经 Ingate 调用使用同一套会话、运行、工具和回答界面。
- Ingate 模式只选择产品层的 Gateway、Route 和逻辑模型，不向用户暴露 Envoy 或 xDS 实现。
- 用户看到的是一个统一的 Ingate 助手，不需要理解内部 Agent 数量。
- 工具活动用于说明助手检查了什么，不模拟或展示模型思维过程。
- 依据紧邻相关结论展示。
- 实时资源依据和产品文档依据使用不同标识。
- 失败记录保留原问题，并提供明确的重新运行入口。
- 修改建议可以使用文本或结构化差异展示，但不得附带执行按钮。
- 页面应明确说明助手提供的是诊断建议，最终修改由用户完成。
- 首轮交付可以先完成后端和 API 验证，Console 在后续用户故事接入。

## 7. 技术考虑

- PRD 不指定 Eino、Google ADK、LangChainGo 或其他 Agent 框架。
- SPEC 阶段应通过最小验证比较候选框架，而不是先建设完整基础设施。
- 产品概念应能映射到成熟实现普遍采用的会话、运行和事件模型，例如 [OpenAI Codex](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)、[Google ADK](https://github.com/google/adk-docs/blob/main/docs/runtime/event-loop.md) 和 [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/running_agents/)。
- 上述实现仅作为设计参考，不构成框架依赖。
- Assistant 只能通过正式产品边界读取资源，不直接访问 etcd。
- 首版不识别或持久化管理员身份，全部会话在当前 Ingate 内共享；Assistant 只允许部署在 Console 可访问的内部网络。
- Assistant 的模型连接是通过产品 API 管理的持久状态；进程配置只包含 HTTP、MySQL、Admin API 和保护已保存凭据所需的基础设施参数。
- 直连模式使用 OpenAI-compatible 协议；Ingate 模式使用 AI Route 发布的逻辑模型名，实际厂商、实际模型和供应商凭据继续由 Route 与 Service 管理。
- 模型连接中的 API Key 和 Caller Access Key 写入后不可读回，持久化前必须由应用加密。
- 会话、运行和内容项是逻辑产品概念，不预先决定数据库表数量。
- 流式传输方式、持久化结构和内部事件映射由 SPEC 决定。
- Temporal 不属于产品要求，只有出现真实的长任务、暂停恢复或可靠后台执行需求时才重新评估。
- 现有 Assistant 骨架可以保留、修改或删除，不作为兼容约束。
- 后续增加只读工具时，应通过新增能力和内容类型扩展，不修改已存在内容的含义。

## 8. 成功指标

- 预设的 5 个 Gateway、Route 和 Service 排障场景中，至少 4 个得到正确结论或正确声明证据不足。
- 所有涉及实时配置、版本和状态的断言均有资源依据。
- 所有涉及产品规则的断言均有文档依据。
- 用户可以查看每次诊断使用过的只读能力。
- Assistant 对外暴露的写入能力数量为零。
- 管理员可以通过 API 完成直连和 Ingate 两种模型连接配置，且读取结果不包含明文凭据。
- 切换模型连接不需要修改 Assistant 配置文件或重启进程。
- 页面刷新和 Assistant 重启后，已经完成的会话内容均可恢复。
- 用户能在 2 分钟内完成提问、检查依据和获得建议的人工验收流程。
- 核心 API 端到端验证可以通过一个命令重复运行。

## 9. SPEC 必须明确的技术契约

- 候选 Agent Runtime 的最小验证结果。
- 模型连接 API、两种连接模式、凭据更新语义和加密方式。
- 会话、运行和内容项的最小持久化模型。
- 运行时事件如何转换为用户可见内容项。
- 工具结果需要保留的安全摘要范围。
- 流式响应使用的协议。
- Assistant 读取产品资源的正式接口。
- 内置文档的最小检索方式。
- 模型提供方的接入边界。
- 确定性端到端验证使用的模型替代方式。
- 会话保留期限及容量限制。
